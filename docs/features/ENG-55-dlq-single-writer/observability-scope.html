Observability scope for the secondary test

ENG-55 · DLQ item movement violates single-writer-per-partition · decision input, not a commitment

You leaned toward building both tests, but asked to first see what the secondary (“state / GC drift”) test would add to the public interface. This page is exactly that: what stats exist today, what I propose to add, why each field is the minimum needed to make the bug observable, and the cost of growing the wire API. Nothing here is implemented yet.

The crux. The primary liveness test needs no new observability — it watches a blocked QueueLease on the dead-letter queue. The secondary test is different: the state it must observe (the Logical’s in-memory view of the DLQ partition) is not exposed anywhere today. So “build both tests” necessarily means “add fields to the public QueueStats API.” That is the scope you’re weighing.

Why storage-derived stats can’t prove this bug

The current bug writes the dead-lettered item directly to the DLQ’s storage partition. So the item is physically in storage. Every stat we expose today is read from storage (partition.Store.Stats()) — meaning total, scheduled, and the age averages all already reflect the item, on main and on the fix alike. They cannot distinguish buggy from correct.

What the bug actually corrupts is the Logical’s in-memory bookkeeping for that partition, which the direct write skips entirely:

  • In-memory un-leased count (p.State.UnLeased) is never incremented — the Logical doesn’t know the new item exists for distribution purposes.
  • The partition’s lifecycle/GC timer (p.Lifecycle.NextLifecycleRun) is never advanced — so the item’s ExpireDeadline isn’t scheduled for GC on time (defect #2 in the ticket).

Neither of those is on the wire today. That’s the gap the secondary test forces us to close.

Proposed addition — the minimal set

Two new fields on QueuePartitionStats (and the internal types.PartitionStats + the handleStats handler that fills them from live QueueState). One field per defect.

FieldTypeSourceWhat it makes observable
unLeased ADD int32 in-memory p.State.UnLeased The Logical’s own count of available items in the partition. On main after dead-letter this stays stale (e.g. 0) while total reads 1 from storage — the divergence is the bug. On the fix, unLeased == total.
nextLifecycleRun ADD string (duration) in-memory p.Lifecycle.NextLifecycleRun When the partition’s GC/expiry routine will next run. On main after dead-letter it stays far in the future (the timer was never advanced). On the fix it moves up to the item’s ExpireDeadline. This is the direct observable for defect #2.

How the secondary test would use them

// Drive a source item to dead-letter, then poll the DLQ's public stats:
require.Eventually(t, func() bool {
    stats := mustQueueStats(t, c, dlqName)
    p := stats.LogicalQueues[0].Partitions[0]
    // In-memory view agrees with storage  -> single-writer path ran
    // GC timer advanced to the item's expiry -> lifecycle was notified
    return p.UnLeased == p.Total && p.UnLeased == 1
}, 10*clock.Second, 100*clock.Millisecond)

On main this never becomes true within the window (in-memory unLeased stays 0 until an unrelated wake re-syncs it); on the fix it’s true almost immediately. Same shape as the primary test, but asserting the internal accounting rather than consumer delivery.

Considered and deliberately excluded

  • mostRecentDeadline — also drifts, but it’s redundant with nextLifecycleRun for proving the defect, and it’s a less meaningful operator signal. Excluded to keep the surface minimal.
  • A separate /debug-only endpoint instead of first-class stats — keeps the permanent public API smaller, but adds a second observability mechanism and a test-only surface the surface-testing philosophy discourages. See the open question below.

Cost of growing the public surface

  • Permanent wire contract. Proto fields are forever — once unLeased / nextLifecycleRun ship, clients may depend on them and we can’t quietly remove them.
  • A new invariant to honor. Exposing “in-memory unLeased vs storage total” tacitly promises they normally agree — which is precisely what we’re fixing, but it also means any future divergence becomes a visible, supportable contract.
  • Genuinely useful, though. Both fields help operators independent of this bug: unLeased surfaces distribution skew, and nextLifecycleRun exposes the GC cadence that is otherwise invisible. They are not test-only scaffolding.
  • Mechanical footprint: 2 proto fields, regenerate (make proto), 2 fields on types.PartitionStats, ~4 lines in handleStats to copy from QueueState, and the client mapping. Small.

The decision in front of you

The primary liveness test proves the bug and the fix on its own, with zero API change. The secondary test buys a second, independent proof (in-memory accounting + GC scheduling) at the cost of two permanent fields on the public QueueStats contract.

Three ways to go:

  • A. Both tests, fields as first-class stats — the scope drawn above. Recommended if you value the operator-facing unLeased / nextLifecycleRun signals anyway.
  • B. Both tests, behind a debug-only surface — proves the same thing without a permanent public-API promise; adds a separate observability mechanism.
  • C. Primary test only — smallest change; the GC-drift defect is fixed but only indirectly verified (via the liveness behavior it shares a code path with).

Once you pick, I’ll fold the answer into the Blueprint’s Testing and Architecture sections and continue.
